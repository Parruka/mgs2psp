2. HOW EACH KIND IS SWITCHED OFF, AND ITS PROOF
Code: ge/bound.h (masks), boot/nat_stub.h (bd_setup, rt_bound_at, rt_nat_f1_at), boot/xlive_chk.c + psp/xl_psp.c (the
transfers by chain; the turn's lines), ge/gelive.c (gl_bd_out: call by call), ge/fxthin.c (the rain owners' blocks).
- K1 ship: the native path's arm 3 becomes arm 4 for the pictures of the turn: the builder's stub does the game-side work
  (the VU memory's state as always) and the groups are not handed on, so nothing of the ship is converted or drawn.
- K2 people, K5 stage program: the transfer of chain 2 / chain 10 of the frame's list is left out before it is queued
  (bd_drop_chain); the game's own DMA state moves as always.
- K3 sorted primitives and meshes: inside chain 6's walk, every call that is not the rain's is left out (gl_call; the rain's
  calls are known by their owner blocks, ge/fxthin.c). The VIF walk of the left-out calls still runs, so K3 UNDER-measures
  chain 6's cost by the walk's share [C code].
- K4 rain: the rain owners' calls are left out but the last MGS2_GL_RAIN_NEAR (cfg: 1) of each picture's 4 drop-sheet calls.
  The sheets come far to near in the sorted chain in 24 of 25 sampled pictures [C twin probe], so "last" is "nearest".
  Per turn in the rain wait: 5,200 rain calls (200 sheets), 5,150 left out, 50 kept [C twin = emulator]. The same
  under-measure as K3. Its own whole-run switch is MGS2_GL_RAIN_CUT=1 (with MGS2_GL_RAIN_NEAR), state-exact on the twin.
- K6: K1 + K2 + chain 6's whole transfer left out (the rain with it).
- K7: every transfer left out; the turn is the main CPU's and the ME rests (no walks, no lists). The builder's stub stays arm 3
  and its recorded groups are dropped by the main CPU ('natg' in the bound line), so the main CPU's game code does K0's work.
What "chain N" means changes with the scene (a chain's number is its place in the frame's list) [C emulator, gl37's log]:
  rain: chain 2 people, chain 3 the native ship groups, chain 6 the sorted chain, chain 10 the stage's program;
  first deck scene: the ship's native groups are in chain 4, chain 2 and chain 7 are other things;
  steady deck: no native ship groups; chains 3, 10 and 14 carry the picture.
  So K2 / K5 / K6 leave out "the transfer at place 2 / 10 / 6" and only mean people / stage program / sorted in the rain.

4. F1 (gl37's fix_design.md option A)
- Built behind its own switches: MGS2_NAT_F1=1 (every turn), MGS2_NAT_F1_CYCLE=<a digit a turn>, MGS2_NAT_F1CHK=1 (check).
- What it does [C code, ge/xlate.c xl_f1_begin / f1_plan / xl_f1_end]: before a run of native ship groups is fed, the run's
  records are read backwards per VU buffer and each group that writes nothing a later group of the run does not write again
  takes xl_p04_fast's existing skip branch (XR_SKIP: the matrix, tag template, header and counts as always). Tests at the
  run's start (the VU program at 0x1be is df0, the buffers in range and apart, the state the fast form needs); every group
  must end with an MSCAL, or the run is not planned. A group without the fast form by its record is a BARRIER: it is fed in
  full and the groups before it are planned as a run of their own (the re-use notes' rule). Replayed runs are left alone.
- Differences from the design note: (1) the note asked for runs whose every group has the fast form; that planned only
  39 % of the groups (none in the walk), so runs are planned by segments between barriers; (2) the check mode re-plans a
  run with the groups that declined when they ran as barriers before it compares (the first plan predicts them fast; the
  run-time decline writes the same quadwords: gl36's "replays with a decline" case, counted apart).
- Proof [C]: twin, F1 whole run: 685/685, every frame and column = the plain arm; 33,384 runs planned, 1,610,127 groups,
  1,233,041 not written (77 %), 299,619 barriers, 0 runs not planned, 0 problems. Check mode, twin, re-use recording every
  run: 2,226,860 groups compared, 0 DIFFERING, 0 written by the plan and not by the notes, 904 the decline case. Check mode
  with the revised schedule: 140,346 compared, 0 differing. Emulator check run (no-PGO build): 62/62, 567,749 compared,
  0 differing; final build: 62/62, 7,016 runs planned, 731,605 groups, 567,299 compared, 0 DIFFERING (emu_f3).
- In the cfg F1 is ON in four turns: 24,400 (first deck scene), 29,900 (K0 R0), 30,100 (K0 R1), 31,000 (walk, K4 R0).
  Under the re-use's R1 few groups are left for F1 (the replayed runs are not planned), so the R1 turn is a proof of the
  two together more than a measure.
