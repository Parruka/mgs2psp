The build is exact and every gate passes: build_gl32/deliver, EBOOT 5646bcec. The twin's hashes and every frame's digests are
the same with the cache on and off (685/685 hash lines, 17,664 frames); the check mode converted 1,086,665 found entries again
with 0 differences on the delivered route (1,632,614 with 0 on the cache-everywhere route, 804,657 with 0 on gl31's route,

455 pictures byte-identical to gl31's emulator pictures (the 455th is the known noise frame 24,784). BUT THE COST MODEL SAYS THE
CACHE IS NOT WORTH ITS CODE [C model]: against this EBOOT's own no-cache arm the cache alone saves 4.1 ms a picture in a
Media Engine turn of the rain wait and 3.1 ms in a main turn (about 1 percent), and nothing in the rain walk (-0.5 / +0.4 ms);
leaving the static streams in RAM instead of copying them (my addition, arm 3) saves 11.7 ms more in ME turns only. And this
EBOOT's no-cache arm is 7 to 13 ms a picture SLOWER than gl31's native arm in the same model (I-cache misses: more code on the
ship's path), so against gl31 only the arm-3 ME turns of the rain wait come out ahead, by 2.6 ms. Exact identity cost nothing;
the gain was never there: the per-vertex conversion is 4.7 ms of the ship's 75 ms of work a picture (step 1). I built a second,
diagnostic ELF without the cache code (in-place streams only): -5.6 ms against gl31 in the ME turn of the rain wait, still
+3.7 ms in the main turn. The lead decides whether gl32 is worth a PSP run; the options are in section 9.

4. STEPS 3-5, THE DESIGN AS BUILT
Exact output first, and it cost nothing: there is no non-exact path in the build.
 - Static rule (stub, the same on every platform): native arm, the cache key on, the DF0 entry, all three streams sent, each
   outside packet memory. Such a group is flagged in its 48-byte record and carries the generation (a counter the stub bumps at
   every object make, colour-buffer free, static lighting, and when the stage's code changes).
 - The cache (ge/natvc.h, the picture's side, ME-safe): one block; key = the three stream addresses + the vertex count; an
   entry holds the positions' box and a 'draws nothing' bit when first met (40 bytes), and the converted vertices (16 B each,
   the GE's format), strips and indices once the group is first drawn (a group the off-screen cut always removes takes no
   data). Everything that depends on the call is computed per call as before: matrix, cut, depth range, GS state, texture,
   the alpha byte (patched in the entry if it differs; 0 times on the route). The cached vertices are COPIED into the frame's
   own vertex memory, so the GE never reads the cache and the frame's bytes are the same with and without it.
 - Dropped whole: when a group's generation differs from the cache's, when 3 of 4 entries are used, when the data area is full.
 - Check mode (twin, MGS2_NAT_VC_CHK=1): every found entry is converted again from the streams and compared (box, vertices,
   strips, indices). Static check (twin, MGS2_NAT_STCHK=8): every static group's three streams are hashed again at each of
   the next 8 vblanks' starts.
 - Arm 3's second bit: for a flagged group the main CPU plans no copy of its streams; the ME's walk reads them in RAM (the
   path gl30n already has for data outside the copy).
Memory [C]: the block is 256 KB = 2,048 entries (80 KB) + 175 KB of data. On the delivered route to 31,400 (twin and emulator,
the same counts): most in use 1,492 entries and 174 KB, both in the turn 26,000-26,100 (1,911 different groups, each met once;
the one drop for want of data, 1 group not stored); on the deck from 29,000 at most 617 entries and 116 KB, 0 drops for want
of room. The census's simple simulation needed 384-512 KB for the deck; the two-step entry is why 256 KB is enough.
 - PSP: the block comes from the heap (memalign), because the copy arena is in the ME's eDRAM. gl30's PSP log had about
   2,732 KB of heap free at its lowest [C PSP gl30]; the block and 16 KB of larger image leave about 2,460 KB [I: 2,732 - 272].
   If the heap refuses, the log says 'NOT MADE', the cache stays off and the pictures are the same [C code].
 - Emulator: its heap also holds the 3 MB copy arena and has 140 KB free at its lowest, so there the block is the arena's
   last 256 KB (arena 2,816 KB instead of 3,072). This is an emulator-only difference and it shows once: see G3.
 - The frame arena's whole-run maximum was not needed for this placement and was not measured.

 - Three arms (0,0,1,1,3,3) instead of the plan's two (A / B). Arm 3 adds 'static streams left in RAM for the ME', which the
   plan did not ask for; I added it when step 1 showed the copy (14.4 ms) is three times the vertices (4.7 ms). It is behind
   its own bit, proven on the twin's late-walk mode, and MGS2_NAT_VC_CYCLE=0,0,1,1 gives the plan's pure A / B with this EBOOT.
   With three arms each arm gets 3 turns of the 9 in the rain wait instead of 4 or 5.
 - The GE does not read the cache: cached vertices are copied into the frame (1.07 ms a picture in the model). Reading them
   in place would save that copy and would need the cache to outlive the frames that point into it; not built.

   PSP's allocation, and shows 41 undone plans in one turn that the PSP should not.

 - The model's no-cache arm is not gl31's arm 3 (section 6): the changed functions lost their gl20 profiles and the path
