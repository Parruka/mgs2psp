3. THE PROFILING EMULATOR'S FLOAT BUG (found while tracing; not a gl39 bug)
- Symptom: trace run t0 of the use build differed in 2 of 61 hash lines (vb 30,000, 30,500); identical runs gave two outcomes
  (3 of 7 runs with a profile window at 29,601 differed, 0 of 3 without). What differed in the EE RAM at 30,000: 6,704 bytes, two
  chains of points and their matrices; no counter.
- Cause [C, code read + counted]: the patched PPSSPP (ppsspp_prof, PspProf) runs profile windows in its interpreter. The
  interpreter computed mul.s, div.s, sqrt.s and cvt.s.w in the HOST's rounding mode, which the local patch set only at a slice's
  start and at ctc1. After a thread switch inside a slice the host mode was the previous thread's: a thread with the kernel's
  default FCR31 00000e00 (idle, battery, callback threads) leaves round-to-nearest for the game's thread (FCR31 01000001).
- Proof [C]: a second binary build/PPSSPPHeadless_fcr computes the four operations in the thread's own FCR31 mode and counts.
  Window 29,601-29,606: 1,385,128 such operations, 30,002 in another host mode, 9,359 with another result, at game code addresses.
  With the old results kept (PSPPROF_FPU_HOSTMODE=1) 4 of 4 runs differ with the old value; with the fix 4 of 4 are equal.
  gl38's build has the same artefact (6,394 wrong results in the same window; its hashes happened to stay equal there).
- The original binary build/PPSSPPHeadless is untouched (md5 50406ec1...). The patch: attic/gl39/tools/
  ppsspp_pspprof_fcr_2026-11-23.diff (82 lines: Core/MIPS/PspProf.h, MIPSInt.cpp, PspProf.cpp). pgo.sh is not edited: PPF in the
  environment names the binary.
- The model's counts did not move: gl38's final build run again on the fixed binary against gl38's own model runs of the same
  turns: +0.01, -0.48, +0.04, -0.39, +0.19 ms a step (instructions within 0.23 %, I-misses 0.65 %, D-misses 1.24 %) [C model].
- With the fix every profiled run of gl39 is hash-equal: traces t0 61/61, t1 117/117, t2 62/62; model runs ka39, km39, kf39, kd39
  62/62, dn39 60/60; gl38's build k38x, k38y 62/62 (gl38's report F6 had 1 to 9 differing lines in such runs).
- UNKNOWN: why the old binary's runs were sometimes equal (the emulated timeline is not the same in every run).
- The second trace problem (t1's windows of 0.8-1.5 thousand million instructions, which filled the disk): [I] the training cfg's
