Asked by Ffm (2026-10-23 10:37): "can we do a check of the work we have done until now? to see if there is any bugs, mistakes or anything that we missed?"

**Scope and method.** A read-only review of `/mnt/project-files/mgs2/` (notes, `recomp/`, `runtime/`, `boot/`, `ge/`, `psp/`, `tools/`, `prof/`) and the project memory. Snapshot: 2026-10-23, 10:38 to 11:10 UTC. The MGS2 port thread was writing renderer_notes.md §11.8-11.9 and `psp/ge_replay` (v5) during the audit, so quotes are the text as it read then. ## 1. High

### H1. A full stage's code was never sized, and by the measured expansion it does not fit

**Finding.** Every PSP build so far uses coverage-reduced code. Each function that the scripted boot-to-deck run never entered becomes `rt_missing`, which stops the run there. Only a small share of the functions is kept. So every memory, size, I-cache and code-order number so far describes the reduced code. No note compares the full code with the PSP's memory, and the measured expansion makes the full code several times larger than the room left for it.

**Evidence.**
- **Reduced builds:**
  - psp_harness.md:40: the PSP builds use the reduced headers from `tools/prune_cov.py`.
  - tools/prune_cov.py:2-4: "Exact only for runs that enter the same functions as the coverage run".
- **Functions kept** (boot/cov_u_w01a.txt), against the totals in recomp/README.md:14-15:
  - ELF: 1,119 of 2,222.
  - w00a: 987 of 6,445 (README: "w00a + ELF 8,667 functions").
  - Other stages kept: w01a 873, d00t 1,024, d01t 546, n_title 322.
- **Expansion:** about 8 PSP instructions per guest instruction, or about 32 bytes (speed_notes.md:192):
  - reduced w00a: 86.6 k guest instructions -> 2.76 MB;
  - reduced ELF: 71.0 k -> 2.36 MB.
- **Full sizes at that ratio [I]**, assuming the stage images are code from end to end, as stage_notes.md:12 describes:
  - w00a: 2,258,944 bytes = 565 k instructions -> about 18 MB;
  - ELF: 483,268 bytes = 121 k instructions -> about 4.0 MB;
  - w11a: 3,049,472 bytes -> about 24 MB.
- **Room:**
  - The stage overlay arena is 4.3 MB (psp/main_psp.c:295, `OVL_SIZE 0x450000`).
  - The largest free heap block at the end of the v23 run is 2.9 MB (see M2).
- **Earlier planning:**
  - feasibility.md:58 names code size as a risk.
  - feasibility.md:90 took Peace Walker's 1.0-1.3 MB of native code per stage as the model, which does not hold for translated code.
  - The dedup estimate (stage_notes.md:17: about 5.9 MB of distinct guest code over all 123 images) shrinks the total on the memory stick, not what one stage needs in memory at once [I].

**Why it matters.** This decides the code form the recompiler must produce, before the full port is attempted. It also decides whether tuning cold functions one by one is still worth it. The reduced harness is a sound timing tool; only its sizes are not the port's.

**Fix** (exact options):
1. **Measure first.** Link an unreduced ELF and w00a overlay once with the PSP toolchain and record the text sizes. No run is needed.
2. **Then choose, with numbers:**
   - hot functions stay as today;
   - cold functions in a compact exact form: `-Os`, or a small interpreter, like the VU0 one, for code never seen in coverage;
   - translated code loaded from the memory stick in groups, a finer form of the overlay mechanism;
   - guest RAM sized to what MGS2 actually touches. This is feasibility.md:58's own mitigation; it needs a high-water measurement.

### H2. "The deck frame fits 40 ms on the GE" was measured with the CPU idle

**Finding.** MGS2GE builds the list first, then runs it alone and waits for it:
- psp/ge_replay/main.c:5-6: "list built first, then run alone and waited for, so the two do not overlap";
- the part and frame loops: build, then `sceGuSync` wait, then time only the GE run.

In the port, the GE draws one frame while the CPU runs the next two logic steps on the same bus. The only measurement with the CPU busy (v1) added 21 ms.

**Evidence.**
- v1 on the PSP (renderer_notes.md:265, :274): full frame 75.11 ms on the GE; with the CPU copying at the same time 95.98 ms (+20.87 ms, +28%).
- v3 best 38.32 ms (renderer_notes.md:317).
- v4 transformed with fog 38.90 ms (prof/hw_ge_v4/log.txt:22; renderer_notes.md:495: "under the 40 ms of 25 fps").
- The v23 model's deck step makes 65.2 k D-misses and 50.0 k I-misses (psp_harness.md:194).

**Why it matters.** v4 leaves 1.1 ms of the 40 ms. v1's copy loop is a worst case and the game's load is lighter, so the true cost lies between 0 and about 21 ms [I]. Until it is measured, "fits" is not shown.

**Fix.** One MGS2GE mode that times the frame's list while the CPU runs a load with the logic step's measured miss rate (D- and I-misses per ms, from the v23 model). Report the GE time next to the idle number.

### H3. The 25 fps estimates leave out IOP and sound; the numbers given to Ffm are optimistic

**Finding.** renderer_notes.md §11.6 adds two logic steps and the renderer's CPU time. But the harness's "logic" column excludes IOP and sound (psp/main_psp.c:215: logic = step - IOP - GS - draw).

**Evidence.**
- **The estimates:**
  - renderer_notes.md:416, deck: "logic 2 x 33.5 + about 22 gives about 89 ms ... With the logic levers ... about 64 ms (15-16 fps)".
  - renderer_notes.md:417, crew deck: "2 x 15.2 (hardware v18) + about 10 gives about 40 ms, close to 25 fps".
- **IOP and sound per step:** deck 2.83 ms (prof/hw_v23/steps.csv, mean of 1,200 steps); crew deck 1.90 ms (prof/hw_v18/steps.csv).
- **Recomputed** (the same method plus IOP and sound):
  - Deck: 2 x (33.44 + 2.83) + 22 = 94.5 ms (10.6 fps).
  - Deck with the §38 levers (10-14 ms per step): 66.5-74.5 ms (13.4-15.0 fps).
  - Crew deck: 2 x (15.20 + 1.90) + 10 = 44.2 ms (22.6 fps).
- **What Ffm was told** on 2026-10-21 at 19:38 (project memory): deck 15-17 fps, crew deck close to 25.
- **The crew deck has had no hardware run since v18;** v19 to v23 ran the deck route. The v23 model gives w01a 25.21 ms per step (psp_harness.md:194), against 27.97 on hardware in v18, so its real number today is unknown.
- **The same mix-up in speed_notes:** speed_notes.md:426 calls 38.78 ms (81.89 - 32.71 - 10.40) the deck's "logic" on hardware, but that figure includes IOP and sound.

**Fix.**
- Add an IOP and sound line to §11.6.
- Give Ffm the corrected range with the next numbers.
- Run the w01a route in the next harness build. Both routes are already supported.

### H4. Audio output is neither built nor in any budget

**Finding.** The SPU2 model runs in state-only mode. Nothing mixes the voices or the streamed PCM, and there is no reverb. No budget line covers audio output, and none says it is assumed to run on the Media Engine.

**Evidence.**
- runtime/iop_host.h:510-511 ("state-only mode ... no samples mixed yet") and :516-517.
- sound_notes.md:30 (the model has no reverb; "Both matter for MGS2") and :42 ("Not done yet: mixing ... reverb").
- sandstone_review.md:68-75 (PS2RC):
  - its spu2_lite has no reverb, noise, pitch modulation or AutoDMA;
  - its Media Engine split saved 5.8 ms per frame on GTA;
  - the main CPU kept a state-only engine costing about 40% of the full mix.
- renderer_notes.md §11.6 and speed_notes.md §38 have no audio term.

**Why it matters.**
- Mixed on the main CPU, audio would cost something of the order of PS2RC's 5.8 ms per frame, plus reverb [I: GTA's number, not MGS2's].
- On the Media Engine it costs little main-CPU time, but it is then a plan item with its own memory and thread needs (research_review M15).

**Fix.**
- Write the assumption into §11.6: audio output runs on the Media Engine, or through sceSas. sceSas is a research item; it needs a listening comparison, and Ffm's consent if it sounds different.
- Size it once the mixer exists.

## 2. Medium

### M1. Where the PSP's FPU and the PS2's differ, the reference follows the PSP (Ffm's decision)

**Finding.** The hash chain proves x86 = emulator = PSP, not x86 = PS2. When x86 and the PSP disagreed in v12-v15, x86 was changed to match the PSP. In that case the PSP's behaviour is the opposite of the PS2's.

**Evidence.**
- **The v12-v15 case** (speed_notes.md:297):
  - At vb 15793 a denormal came from a garbage word (0x0031685c).
  - The PSP FPU returns x + 0 = x for a denormal x. So in 0x11cf88 lane z the PSP computed -d / d = -1.
  - x86, which flushed the denormal, computed -0 / +0 = -Fmax.
- **What the PS2 would have given:** -Fmax, the result x86 had before the change [I, from the R5900 rules the code already states]:
  - runtime/guest.h:122 models the R5900's x/0 = ±Fmax when the divisor is exactly zero;
  - guest.h:106 itself notes that the PS2 treats denormal operands as zero.
- **Other cases on the PSP:**
  - speed_notes.md:306 (probe 11 on the PSP): denormal inputs are used exactly in mul, div, sqrt and compares.
  - The FPU code uses plain operators with no input clamp, so words with exponent 255 act as Inf or NaN on the PSP. The R5900 has neither [general R5900 knowledge, unverified here].
- **No count yet:** the `RDF_DEN` counter of denormal float loads exists (guest.h:106), but no result from it is in the notes.

**Why it matters.**
- These cases are rare: the documented one changed 74 words by 1-3 ulp.
- It is still a departure from the PS2 that the hash rule cannot see. From vb 15793 on, the game state is the PSP's rather than the PS2's.
- Ffm's goal is 99% fidelity, and this is the same kind of choice Ffm made explicitly for the VFPU.

**Fix.**
1. Run x86 with `RDF_DEN` on both routes and count the sites.
2. Ask Ffm, with that count, whether to keep the PSP's rule or to model the PS2's at those sites.
3. Write the choice into the notes.

A PCSX2 run, or an x86 "R5900 FPU" build, would show how far the port drifts from the PS2 over a route.

### M2. The "about 4.8 MB free" figure is the wrong measure, and the free space shrinks

**Evidence.**
- **Where the figure comes from:** renderer_notes.md:418 and the project memory use about 4.8 MB. That is the start-of-run "heap headroom 4096 KB" plus "outside the heap ... total 764 KB" (prof/hw_v23/log.txt:216).
- **It shrinks during each run:** at the end of the run the largest heap block is 2960 KB (hw_v23/log.txt:2161). It was 3056 KB in v21 and 2976 KB in v22 (log.txt:2157 in hw_v21 and hw_v22). So about 1.1 MB is lost during each run, and a little more with each build.
- **What the probe measures:** the largest single malloc (psp/main_psp.c:207), not the total free. It cannot tell a leak from fragmentation.
- **A suspicious start value:** the start reading is exactly 4096 KB in all five runs v19-v23, although the builds differ in size (v23's ELF is 8 KB larger than v22's, psp_harness.md:192). The binary search returns exactly 4096 only when the largest block is between 4096 and 4111 KB, so the start probe may be hitting a limit rather than measuring free space [unverified].
- **The outside part is spoken for:** the 764 KB outside the heap (largest block 512 KB) is also where threads created later get their stacks (research_review M15), so it is not free for renderer buffers.

**Fix.**
- Print `mallinfo()` (arena, ordblks, fordblks) and `sceKernelTotalFreeMemSize()` at the start and at the end of the run.
- Find where the 1.1 MB goes.
- Size the renderer against the end-of-run figure.

### M3. Unexplained hitches of 20-145 ms at fixed vblanks

**Evidence** (prof/hw_v23/steps.csv):
- **vb 24667:** the step takes 145.1 ms. Its draw call takes 93.4 ms, against a median full draw of 30.6 ms (v22: 142.4 / 88.4). speed_notes §35 explained the earlier 1.4 s step (uncompiled VU0 programs, fixed in v22). The remaining 60 ms or so of extra draw time has not been examined.
- **IOP and sound spikes:** 20.9-51.2 ms (median 2.5 ms), at the same 12 deck vblanks (±1) in every run from v19 to v23.
  - In v23 they fall at vb 24010, 24107, 24201, 24270, 24367, 24432, 24530, 24595, 24692, 25000 (51.2 ms), 25034 and 25132.
  - Five of the six slowest v23 steps are among them.
  - There are none on the crew deck (v18), and the notes do not mention them.
- **A likely cause [unverified]:** the PSP reads the disc pak synchronously in the game thread (runtime/iop_host.h:55-63, `disc_pak_read`), so streamed-audio refills would stall it.

**Why it matters.** At 25 fps, one 20-50 ms stall drops one or two frames, and the 145 ms step drops three or four.

**Fix.**
- Log the bytes and time of each disc read, and of each IOP command, in those vblanks (research_review M17's recommendation, which still applies).
- If the reads dominate, the planned stream thread is the cure.
- For vb 24667, run PspProf on the draw call.

### M4. The renderer's CPU estimate pairs the list build of one form with the GE time of another

**Evidence.**
- §11.6 (renderer_notes.md:414) counts "GE list build about 3.3 (merged replay, §9b)".
- 3.32 ms was v1's merged draws (renderer_notes.md:275). Their GE time was 76.62 ms, against 75.11 ms unmerged (+1.51 ms). Line 282 calls that "unchanged".
- The GE times now used (v3 and v4 best, 38.3-38.9 ms) are for unmerged lists, whose CPU build takes 20.02-21.35 ms (prof/hw_ge_v4/log.txt:39-41).
- Joining v4's strips cost the GE 4.65 ms (part test, log.txt:36-37).

**Fix.** Measure the best GE form together with the CPU build of that same form. Until then, carry both numbers in §11.6.

### M5. Thin hash coverage of the deck on the PSP

**Evidence.**
- **PSP:** v23 hashes the deck at vb 24000, 24500 and 25000 only ("hash every 500" in prof/hw_v23/log.txt). Nothing is hashed after vb 25000, although the run goes on to 25200. The dense window (`MGS2_HASH_DENSE=15700:16010`) is in the opening, not on the deck.
- **x86 reference:** it has a hash every 100 vblanks up to 25200 (prof/hashes_x86_deck_v21.txt, 252 lines).
- **The speedup rotation:** cfg 0 / 9 / 10 alternate every vblank from vb 24000. They are checked only through the state they carry to vb 24500 and 25000.

**Why it matters.** A difference in a buffer that is overwritten before the next hash point is never seen, and the last 200 deck steps are not checked at all.

**Fix.** Hash every 100 vblanks over the deck window and once at the stop. Both cost little. A dense deck window like the opening's would also do.

### M6. PPSSPP's interpreter and its JIT drift apart on the deck (not followed up)

**Evidence.**
- speed_notes.md:319: in v17's deck trace run, the ee hash left x86's at vb 24500 and 25000 when interpreter windows ran; "Timing only; not chased yet".
- The PGO profiles and code orders come from interpreter windows (PspProf).

**Why it matters.**
- Profiled windows can run a slightly different game state.
- One PPSSPP interpreter operation disagrees with the PSP. That matters if PPSSPP is ever used as a correctness reference.

**Fix.** Bisect with the split finder over one interpreter window, the same tool as in v15.

### M7. The AutoDMA address step is an untested assumption

**Evidence.** runtime/iop_host.h:516: "Address steps of 512 bytes ... an assumption, not measured" (the demo-audio engine, sound_notes.md).

**Why it matters.** The demo engine decides when to refill from the DMA address. A wrong step changes when it refills, and the state hashes cannot catch that, because no reference comes from a real PS2 [I].

**Fix.** Check against PCSX2's SPU2 AutoDMA address reporting, or against the libsd documentation.

## 3. Low

### Code edge cases

**L1. DIV, DIVU and DIV1 with INT_MIN / -1.**
- recomp/recomp.py:54 and :85 emit `a / b` and `a % b`, and handle only b == 0.
- In C this case is undefined; on x86 it traps (SIGFPE).
- The R5900 gives LO = 0x80000000, HI = 0 [general MIPS behaviour, unverified on the R5900].
- **Fix:** add the case (one compare), so x86 cannot crash and both hosts give the PS2's result.

**L2. cfc1 and ctc1 are dropped** (recomp/recomp.py:144).
- SLES_503.83's text has six cfc1-shaped words, at 0x1adb30, 0x1aea98, 0x1aeb10, 0x1aeb98, 0x1af678 and 0x1b028c (fs 3, 8, 9, 10).
- None has fs 31, and there is no ctc1. Values of fs other than 0 or 31 suggest these are data words.
- The stage images were not scanned.
- **Fix:** have the recompiler warn on any `cfc1 $31` or `ctc1` in a stage image.

**L3. The translator mishandles VIF filling writes** (WL > CL).
- ge/xlate.c:79 steps the address back by CL - WL, and reads input data for every position.
- tools/gsref.c has the same code (:1883) but counts these writes ("!vif filling write", :1860). runtime/ee_io.h:443-444 handles them correctly for VIF0.
- Not seen on the deck [unverified: the gsref census counts are not in the notes].
- **Fix:** add a counter to XlStats so the PSP and x86 checks report it per stage, and port ee_io.h's fill rule when one appears.

**L4. A second MSCNT in a row takes the first entry's continuation again** (ge/xlate.c:124: `last_entry` does not advance on a continuation).
- Exact on the deck: the 8-frame check passed.
- May be wrong for programs that chain more than once [unverified].

**L5. The clipped polygon's back-face sign is computed in plain float** (ge/xconv.c:180), while the main loop's follows the VU's order (`xc_cull`).
- No polygon was back-face culled on the deck (renderer_notes.md:609), so nothing shows there.
- Near-degenerate polygons elsewhere could flip [I].

**L6. F2INT leaves NaN to the C cast, which is undefined** (runtime/guest.h:120).
- x86 gives 0x80000000; the PSP's default for an invalid conversion is 0x7fffffff [unverified on the PSP].
- The R5900 has no NaN: a word with exponent 255 converts by its sign [unverified].
- **Fix:** handle the NaN pattern explicitly, by its sign. That is exact to the PS2 and equal on both hosts.
- The same question applies to fmaxf and fminf on NaN and ±0 in MAX.S and MIN.S [unverified].

**L7. Blob alignment, for Stage A on the PSP.**
- xc_df0 can return blob sizes that are 2 mod 4 (ge/xconv.c:84).
- gsref aligns every blob to 64 bytes (tools/gsref.c:474, `ge_put`).
- The PSP host must align them the same way, or the next GerXform load faults [I].

**Overflow:** under round toward zero an IEEE overflow gives ±Fmax, which equals the R5900's clamp, so plain operators are exact there.

**Rules:**
- 333/333/166 set through `scePowerSetClockFrequency` (psp/main_psp.c:441).
- The exit runs only through finish(), after X or HOME (`psp_exit`, main_psp.c:234).
- No hardware counters: timing uses `sceKernelGetSystemTimeWide`.
