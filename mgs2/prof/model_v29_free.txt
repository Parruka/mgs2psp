4. Code size (bytes) and why the profiled units grew. EBOOT text 3,691,084 (v28 3,515,036, +5.0%); overlays w00a 3,703,408
  (3,246,112, +14.1%), w01a 2,277,760 (2,060,384, +10.6%), d00t 2,377,760 (2,595,744, -8.4%), d01t 2,459,984 (2,677,888, -8.1%).
  Without profiles step 3 shrinks every unit (plain builds: gen.o -7.2%, w00a -6.4%, lean_plan.md step 3), and the overlays built
  without a profile (d00t, d01t, n_title) shrink here too. The profiled units grow because psp-gcc's hot / cold choice follows the
  profile's largest counter: a block counts as hot when it runs at least sum_max / 10,000 times (param hot-bb-count-fraction).
  v28's w00a profile had sum_max 428,148,079, in one of the stage unit's out-of-line helpers that step 3 replaces with inline code
  (gen_mm, RDF, WRF, VLQC2, VSQC2, FDIV are gone from v29's gen_s_w00a.o); v29's has 22,963,360 (w01a 28,012,275 -> 1,359,274), so
  the threshold fell from about 42,800 to 2,300 executions and code run between those counts is now compiled for speed instead of
  size. In w00a the profile made 858 functions smaller (-619 KB) and 225 larger (+45 KB) against the plain compile in v28, 439
  smaller (-76 KB) and 332 larger (+205 KB) in v29. The ELF's units share one program summary (sum_max 2.30 G v28, 2.21 G v29), so
  gen.o's growth (+7.8%) has another cause, not looked at yet. Exact candidate for later: a per-unit hot-bb-count-fraction that
  gives back v28's threshold (about 536 for w00a), modeled on v29's d like the runtime items.
