# MGS2 PSP: the plan to 20 fps on the Tanker deck (2026-11-22)

Written for Ffm after gl36's PSP run. Nothing here was built or run for this note; it reads the logs and notes named at the end.
Marks: **[C]** measured on your PSP or read in code or a log; **[C model]** the cost model, already multiplied by 0.5 for Media Engine (ME) work, because ME savings have landed at about half the model on your PSP [C: cull 0.55, re-use 0.5]; **[I]** my estimate, basis named; **UNKNOWN** with how we find out. Single estimates here have been wrong by 2x before. No [I] or [C model] figure is a result.

## Short answer

- **In the rain (the deck you actually play), 20 fps near full speed is not reachable without changing how the game plays.** Both processors need about 3.4 times less work: the main CPU does 76 ms a step and the ME 84, against 25 each [C].
- **Even with play changes I cannot show 20 fps in the rain today.** Doubling the game step (H3) fixes the game's speed, not the picture: the ME needs about 168 ms for a rain picture [C] and 50 is the limit. Every lever we can cost brings that to about 76-116 ms [I]: 9-13 fps.
- **What each path gives in the rain [I]:** exact only: about 7.5-9.5 fps at 30-38% speed (today 5.9 fps at 24% [C]). With visible cuts: 8-12.5 fps at 33-50%. With play changes: 9-13 fps, at 83-100% speed if the step is doubled.
- **The "steady deck" is a cutscene stage (d01t), not the open deck.** There the main CPU is already at the target (about 25 ms [C]) and only the ME is late (40). 15-18 fps is likely with exact work, 17-22 with small visible cuts [I].
- **The graphics chip (GE) does not cap us at 20 fps.** It draws a rain picture in 27 ms and a d01t picture in 16 [C]; 20 fps allows 50.
- **Visible rain cuts are small:** all rain drawing off is worth about 3-4 ms of the ME's 84 [C model], because the exact cut in gl36 already took the largest part.
- **Not paid yet: sound.** The mix costs about 7.5 ms a step on whichever processor does it [C on the main CPU, v24s]. No picture build mixes sound today.
- **Next:** read gl37; then one measurement build that switches whole kinds of drawing off in turns, so the estimates below become measured bounds; then the first main-CPU build. Section 6.

## 1. Units, and what the "steady deck" is

- One game step = one vblank = 1/50 s of game time. A picture is shown every 2 steps. fps = 500 / (ms a step); game speed = 20 / (ms a step).
- 20 fps near full speed = 25 ms a step on **both** processors. The slower one sets the step. 25 fps at full speed = 20 ms.
- The window vb 26,300-28,700 is stage d01t, a demo (cutscene) stage: faces, no player control, no rain [C: design note, game code read there is `S_d01t_*`]. Its steps come every vblank (wait word 0) [C: gl28 steps.csv], so the units above hold.
- So that window says nothing about the open deck. The deck you play is stage w00a, and in our run all of it is in the rain (wait 29,200-30,400, walk 30,800-31,400). **The 20 fps target has to be judged on the two rain rows.** The earlier "deck at 12.5 fps" was the cutscene.

## 3. The GE, and costs not in the numbers yet

- **GE drawing time:** 16.4 ms a d01t picture, 27.1 ms a rain picture [C: gl28 log, 805 and 1,329 ms for 49 lists]; gl22 measured 21.8-27.0 on the deck [C]. The 39-45 ms in the lead plan was measured before the rain cuts [C]. Limits: 50 ms at 20 fps, 40 ms at 25 fps. It fits both.
- **It still costs CPU time.** The GE shares the memory bus: the CPU ran at 75-83% speed while the GE drew [C, older run]. At 20 fps the GE would be busy 33-54% of the time instead of about 16% today, so expect CPU steps 5-9% longer [I: design note 4.3]. The real CPU target is nearer 23 ms of work as measured today. People skinned by the GE add 1.3-4 ms a picture [I].
- **Sound:** +7.5 ms a step if the main CPU mixes it [C v24s]; on the ME it cost the main CPU 0.1 [C v26me2], and the ME's own time for it was never measured (about 7.5 [I: same code]).

**H3, exactly.** The game would run 25 steps a second and every step would move the game twice as far. Every speed, timer, animation rate, AI counter, camera constant and script wait is doubled, for the deck's 106 actor kinds and the shared libraries [C: halfrate note]. What changes for you: collisions are tested over twice the distance (thin walls can be passed), guards react in 40 ms steps instead of 20, the pad is read 25 times a second, and animation blends are coarser. The hash test stops working from the first doubled step, so the PC twin can no longer catch bugs; every area is checked by eye and by play. The recorded pad route no longer fits. Gain: the main CPU may spend 40-50 ms a doubled step instead of 20-25, and logic runs once a picture. After the exact work that is 33-48 ms a doubled step [I: logic 13-22, full pipeline 15-20, IOP 5], so 83-100% speed. It does nothing for the ME. The cheap form (the game's own wait word at 2) only gives half speed [C twin], which is what a slow PSP gives already.

**Pacing (in the notes as A', display only):** show a picture every 3rd step when the picture is late. The main CPU alone then sets the game's speed, the ME sets the fps, and fps is capped at 16.7. One build.

## 5. Three honest paths

Step = the slower processor. Ranges are [I] sums of the levers above; the two CPUs' end figures use the notes' own end state (game code 28-40 ms after the logic work [I, NOTES]) widened for the 2x rule. The design's own end figure for the ME was 25-45 ms a picture [I]; the ship alone costs 35 ms a picture today after five builds [C], against 2-5 in that design, so I do not use it.

- With the pacing switch, game speed in paths 1 and 2 follows the main CPU alone: rain wait 44-67%, walk 40-57%, d01t 80-100% [I], at the same fps.
- **20 fps in the rain: not reachable in paths 1 and 2.** Visible cuts do not touch the main CPU [C model], and its game code stays at 30-45 ms a step [I].
- **Path 3 reaches the speed, not the fps.** 20 fps needs the ME's rain picture under 50 ms; the levers listed give 76-116 [I]. What closes that gap is UNKNOWN. The measurement build in section 6 will say whether it can close at all.
- Main risks: path 1, many builds for about 2-3 fps in the rain, and each exact proof can fail (H1 did). Path 2, the retained ship's memory and GE clipping; you would be trading rain and blur for 1-3 fps. Path 3, H3 is a rewrite of the deck's timing that only play-testing can check, and it still leaves the picture at 9-13 fps.
- Sound (7.5 ms on one processor) and the GE's bus share (5-9%) are not in any row.

## 6. Recommended next builds

1. **gl37 (in build): finish and run it as planned.** It closes the ship's per-group work. If its fixed-work cut lands under 2 ms a step, stop shaving ship stages: gl34-gl36 each bought 1.3-2.7 ms of 85 [C].
2. **gl38: a bound-and-timers build.** In turns, do not draw one kind at a time: ship, people, sorted effects, all rain drawing, the stage blur program. Add timers inside the list build and the people path, and one turn pair with the ME resting. The game stays exact; the test turns show incomplete pictures. Why second: one run turns about ten [I] and UNKNOWN figures above into measured bounds, before we spend ten or more builds on them. If the ME is still over 25 ms a step with all four kinds off, 20 fps in the rain is closed for good and we stop chasing it.
3. **gl39: the main CPU's first build.** 5-10 of the hottest game functions in native C, in turns, plus code generator step 4 in its own turns. Why: the main CPU is at 76 against 25, it becomes the limit after 9 more ms of ME savings [C], and the native-C factor (0.5-0.7 [I]) decides whether Phase 3 is worth its size.
4. **gl40: native people path** (records first, GE skinning in turns), only if gl38's people bound is 10 ms or more. People are the ME's largest chain [C].
5. **gl41: the visible options, with pictures for you:** ripples off, rain drawing off, the blur off, in turns. With its numbers and gl38-gl40's, a decision card on the play changes (rain on its own dice; the doubled step). I would not start either before those numbers.

Order in one line: measure the bounds before building toward them; then the main CPU, because every path needs it; visible and play cuts last, when their price is known.

## Erratum (2026-11-22 13:40 UTC, the lead)
- The cost model's "ms a step" is **ms a picture** (its scripts divide an 80-vblank window by 40 pictures [C: main/attic/gl37/report.txt, build_gl36/mtot35.py]); the PSP's "ms a step" is a vblank. So the 0.5 this plan applies to ME model figures is mostly that unit change, and the ME rows stand.
- **Main-CPU [C model] figures must be halved too**, which this plan did not do: rain logic 6.9 / 4.3 -> about 3.5 / 2.2 a step; B7 -3.4 -> about -1.7; B8 -9.5 / -6.2 -> about -4.8 / -3.1. Path 3's rain main-CPU range moves up by about 3-6 ms. The conclusions do not change: 20 fps in the rain stays out of reach of every costed lever.
- gl37 (main/attic/gl37/report.txt): the ship's fixed-work design reaches only -12..-13.5% of the fixed work (F1-F5, about -1.7..-2.0 ms a step [C model halved]); stopped at its checkpoint. The re-use rule removes the walk loss (+0.9 -> +0.04 ms a step [I]) and keeps the wait gain. Not shipped alone: folded into gl38.
