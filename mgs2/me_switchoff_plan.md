# The ME switch-offs: what we know, what it could be, what I suggest

2026-10-26. [I] = inferred, not measured. Details: `psp_harness.md` "Build v26me2" to "Build v30"; memory `mgs2-me-audio`.

## What we know (measured)

- **5 real power-offs in 34 PSP runs since v24.** Each was a "fresh start" (not sleep), left no crash record (catcher 2 is in every build since v26me4), and battery.txt shows nothing unusual: 71-100%, voltage normal, the low-battery flag never set.
  - ME mixing: **4 of 7 runs** (about 4.0 h): v26me2, v26me3 run 2, v30 runs 1 and 2.
  - ME off: **1 of 27 runs** (about 13.3 h): v24 deck run 1.
  - If the ME made no difference, 4 of the 5 stops landing in the ME runs would be about a 1-in-90 chance by run time (1 in 290 by run count).
- **Same files, same route (v30 indoors):** ME on, 2 of 2 stopped (20.9 min on battery, 20.1 min on USB charging); ME off, 2 of 2 finished (38 min, one of them on battery all the way).
- **When:** 20.1, 20.9, about 22 (the ME-off one, estimated), 38.6 and 39.5 minutes into the run. Each ~20-minute stop came within about 2 minutes after the long hashing stretch, where the battery reading freezes for ~10 minutes in every run (the game's main thread leaves the PSP's own background tasks no time there [I]). Three ME runs passed both marks (v26me4 and v28: 51 min; v29: 40 min).
- **The ME never rests.** With nothing to mix it spins in a loop at full speed. The mix needs about 7 ms of each step, so it spins about 90% of the time.
- **Which battery (2026-10-26 19:52):** Ffm: most runs on the cheap battery, some not. The logs don't name the battery (the system's "min left" is 4.0 x the percent in every run), but the drain gives a hint: v26me2 (first ME stop, 38.6 min) lost 12% in 38 min; v26me4 on the same route 25%; v29, v30 run 1 and run 4 the same as v26me4 (31-40% per hour). That fits a bigger battery in v26me2 [I]; Ffm (19:57): "probably, since i changed in later versions": the early runs were on the other battery, so the first stop (v26me2, 38.6 min) was probably not on the cheap one, while both ~20-minute stops (v30 runs 1 and 2) were. From v31 the battery log adds the battery's full and remaining capacity (scePowerGetBatteryFullCapacity / RemainCapacity, reads only).
- **Power and heat can't be seen in the logs.** Average drain on battery is about the same with the ME on or off (34-37% per hour); short peaks don't show in 5-second readings, and this PSP's battery temperature always reads 20 C.

## What it could be [I]

1. **Power peaks:** game + graphics + memory stick + the ME at full speed make a peak that the battery's protection or the power circuit cuts. Fits the real power-off with no crash record. Against it: it also stopped on USB at 100%, but USB gives only 0.5 A, so the battery still covers the peaks.
   - Ffm (22:04) asked what the cheap battery could be doing; answered 22:06: its voltage dipping under the PSP's cut-off in a short burst (the power controller switches off at once; 5-s readings can't see it), or its protection circuit cutting out early, or its chip answering the PSP wrongly once; its drain says it holds much less than the 1,790 mAh it claims. Against a battery-only story: v26me2's stop was probably on the OSTENT. Test: v30me5 on the OSTENT after run 2.
2. **Heat:** the ME adds heat for the whole run. No data. Against it: the same stop times on battery and on USB charging (charging adds heat).
3. **The system and the taken-over ME:** the PSP's own software expects Sony's code on the ME. If it asks the ME something and waits, the kernel can hang and switch the PSP off (PS2RC saw that with a suspend). Sleep is held off and the power timer ticked, so a plain suspend is ruled out; other system requests are not. Fits the ~20-minute stops coming right after the background tasks get time again.
4. **A fault the catcher can't see** (in system code): on this PSP an uncaught fault switches it off (the first catcher's self-test did exactly that).

## The codec call (2026-10-27, after gl1's stop; task #62)

**What changed the picture [C]:** gl1 (Media Engine off, the live picture on, the cheap battery without USB) switched itself off 15.8 minutes in, at vb ~15,765: the second stop with the ME off (ME off now 2 in 28 runs; Sony's ME start 0 in about 2.75 h). Emulator shots of gl2 along the whole opening (psp_harness.md "Build gl2", README corrected) show the first **codec call from vb ~15,550 to ~20,000**. **All four stops in the opening fall inside it:** gl1 r1 ~15,765 (36 s into the dense hash stretch), v30 r2 16,900-17,000, v30 r1 18,300-18,400, v24 r1 18,900-19,000.

**What that stretch is for the PSP [C unless marked]:**
- The game thread (priority 0x20: pspsdk crt0's default, `PSP_MAIN_THREAD_PRIORITY` not set; disassembly of crt0.o: `li a2,32`) gives the CPU to lower-priority threads only when it blocks: a disc pack read (sceIoRead), the log write every 100 vblanks, a wait for the GE (gl builds, when the GE is still busy), in ME builds nothing (it spins on the ME's words). The PSP runs the highest-priority ready thread.
- In the codec call the game reads the disc least: 2-5 pack reads per 100 vblanks (PPSSPP, gl2 `MGS2GL2_rt`), against 13-15 in d00t before it. Without the picture it is also a light stretch (v30 run 3: ~32 vblanks/s against ~25 in d00t).
- The dense hash stretch (vb 15,700-16,010, every cfg since v15) sits inside it: one state hash per vblank, 1.9 s each with FNV (v30 and before: 100 vblanks took ~190 s, so the game thread blocked about every 40-95 s), 0.24-0.38 s with state hash 2 (gl1: 100 vblanks ~38 s). Through that stretch the system's battery readings (percent, mV, "min left") stood still for minutes: in v30 runs 3 and 4 and v30me6c run 3 they changed once between vb 15,500 and 16,100, each time at vb 15,899-15,901 (t 973-989 s; run 3 mV only, run 4 percent and min left, v30me6c mV and min left), the same game moment in all three [C, battery.txt]. Outside it they change every 29-44 s before it and every 16-22 s just after it (one change in 612 s inside vb 15,500-16,010 in each run; counted on the three battery files). So the readings are refreshed by something that runs only when our thread lets it [I, strong]; why at vb ~15,900 is not known (window 15,800-15,900 has 6 pack reads, 15,900-16,000 has 4, v30 run 3 log).
- The two late stops (v26me2 vb 33,600-33,700, v26me3 run 2 34,100-34,200) were in the deck free play, where the game reads the disc not at all (PPSSPP v25f free route: no disc line from vb 30,000) and the ME builds' game thread spins on the ME: there it blocks only for the log write, about every 4.5 s.
- The seventh (v30me5 run 1, vb 3,170-3,200, the resting ME's first run) came in the r_tnk0 load, with 11-46 disc reads per 100 vblanks: it does not fit [C].

**Idea S [I]:** the stops come after or during long stretches in which our game thread leaves the PSP's own lower-priority threads no CPU (6 of 7 fit). Why that would switch the PSP off is not known: nothing in the logs so far (battery normal, no low flag, the ME builds' power callback last flags only the battery level, 0x80 + percent).

**Next, measured not guessed: `MGS2T_gl2d`** (psp/gl2d.sh: gl2 + `psp/v26me_bat.c -DSYS_DIAG`; reads only, user mode, no new writes; built 2026-10-27 14:08, emulator-checked 14:18 (the same as gl2 in every check; psp_harness.md "Build gl2d"), DELIVERED 14:45 after gl2 run 1's stop was read (to `Desktop\mg2 port\MGS2T_gl2d`, same cheap battery asked); reader `tools/dev/sysdiag_read.py`): (1) every power event written to battery.txt the moment it comes (a power callback): a stop the system announces is in the file before the power goes, none means the power went without the system's word; (2) in each 5-s line, the longest wait of a thread at priority 0x6F that asks to wake every 10 ms (= how long the system's own low-priority threads waited) and the thread manager's counts (thread switches, returns from idle, idle time); (3) the threads user mode can see, at the start and every 60 s. pspsdk notes `scePowerGetBatteryElec` (the battery current) crashes the PSP in user mode: not used.
