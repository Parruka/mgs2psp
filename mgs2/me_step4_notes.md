# The picture on the Media Engine: build order step 4, the first ME picture build

2026-11-08, task #180: `me_handoff_design.md` section 6 step 4. Container builds and emulator runs so far: nothing for your PSP yet. [C] = measured or read in our code and runs; [I] = my inference; UNKNOWN = not known yet, with how we will find out.

## The parts

- **4a** (done): step 2's ME-safe picture code ported onto gl18's tree (gl17's effects code, the thinning by owner, the rain's exact skips), a PSP build on the emulator.
- **4b-1**: the split on the main CPU. Each transfer leaves a record; the runtime's own walk marks the image data it skips; at the transfer's end its chain is walked again and what the picture's walk reads is copied into an arena; the late walk at the next vblank hook reads that copy through a view (the copy where it has the bytes, RAM elsewhere: the x86 twin's "copy laid over RAM"). Checked on the emulator: every frame's digests against x86.
- **4b-2**: the copy taken at the deadline (the hook that ends the step) instead, with the guards' log (the 12 G0 functions and the runtime's own writes into game RAM).
- **4c** (done): the ME's loop as a main-CPU thread on the emulator (PPSSPP has no ME), with its heartbeat and the take-back: exact with the thread above and below the main thread, in turns and through the hang test.
- **4d** (built in four parts and exact on the emulator, below; the ME itself runs only on your PSP): the real ME: the copy in the eDRAM through the kernel segment with today's register writes (probe 2), the queue and the shared words uncached, the caches handed over, what a heartbeat costs there, a take-back that stops the ME first; the main CPU's own turns walk each transfer from RAM as it ends (it cannot reach the eDRAM).
- **4e**: the first run on your PSP (section at the end). Nothing goes to your PSP before gl18's run is read.

## 4b-1: the split on the main CPU (done 2026-11-08)

  - **The runtime's walk marks the image data** it skips or passes on whole (`runtime/ee_io.h` `XL_IMG` in five places: the GIF's skip of an image and its last quadword, VIF1 DIRECT's skip, the fast path's bulk skip and its one-quadword DIRECT). The texture map's reads go through the same view during the walk. No room in the arena: the records before are walked then and the copy made again.

## 4c: the ME's loop as a thread on the emulator (done 2026-11-08)

- **What it does** (`psp/xl_psp.c` with `MGS2_ME_PIC=3`; the loop `ge/xme.c`, its queue `ge/xme.h`; files in `tools/dev/me18/`: `me18d.diff` (on 4b-2's tree: `ge/` and `psp/xl_psp.c`), `mkpsp18d.sh`, `mkme18d.sh`, `callmap18d.txt`, `piccmp.sh`):
  - **The main CPU keeps** 4b-2's records, plans, filter, guards and log, the thinning's scan (it reads the game's RAM), the GE and the display. **The loop gets**, through a queue of 256 entries: each record as its transfer ends (it copies the bytes from RAM at once), the FILL at the deadline (it lays the log over the early copies; the main CPU waits for it, then empties the log), the WALK (the records walked through their copies; the arena is the loop's until then, and the main CPU waits for it before its next plan or hook), the thinning's ranges, and each vblank hook (the frame's end and its GE list into one of 4 result slots; the frame's start, only once the GE has finished every list before; the texture cache's frame). The main CPU gives the GE each list, one at a time, and tells the loop when the GE has finished one.
  - **PPSSPP has no ME**, so the loop runs as a thread of the main CPU ("me_pic", 64 KB stack, the main thread's FPU rule). At priority 0x30 (the default, below the main thread's 0x20) it runs only while the main CPU waits: the latest the x86 check allows, each walk done by the next hook or plan. At 0x18 (`MGS2_ME_PIC_PRI=1`) each entry is done as it is posted.
  - **The heartbeat**: a word the loop moves at every entry, record and wait, and inside long work (`me_rt.h` `ME_BEAT`: each DMA tag of a walk, each VIF command and GIF tag, each row of a local copy). The place word `at` says where the loop is (between entries, the entry, the walk's record, the wait).
  - **The take-back**: when the heartbeat has not moved for 1 s (`MGS2_ME_PIC_TBK_MS`) while the main CPU waits for the loop, or at a hook with entries waiting and no heartbeat since the hook before (`mq_probe`: the loop is given the CPU until it moves), the thread is ended and the main CPU runs the entries itself from then on. **Warm** when the loop stopped between entries (its place word goes to 0 only after the queue's tail has moved, so a 0 means every entry before is whole): the main CPU runs the entries left and nothing is lost. **Cold** when it stopped inside an entry: the frame being made and the records not yet walked are dropped, the translator starts again as at a restart and the texture cache starts empty (the GS memory picture and the texture map stay).
  - **Turns** (`MGS2_ME_PIC_TURN=N`): every other block of N vblanks the main CPU runs the entries itself, the queue emptied at each change. **The hang test** (`MGS2_ME_PIC_HANG=vb`): the loop stops for good at the first hook at or after vb, with its heartbeat stopped.

## 4d: the picture on the real ME, the design (2026-11-08)

Built in four parts (4d-1 to 4d-4, the order at the end), each exact on the emulator before the next: the results in the next section. The ME's and the main CPU's caches do not see each other's writes: everything below follows from that, from the eDRAM being the ME's alone, and from your PSP's memory.

- **Mode 4** (`MGS2_ME_PIC=4`): 4c's records, plans, filter, guards, log, queue and loop, the loop on the real ME. The emulator has no ME (`hle_me_start` refuses there [C: me_ep.c]): there mode 4 runs the loop as 4c's thread, with the ME's own memory (below) in main RAM, so every part but the caches and the eDRAM is checked there.
- **The main CPU cannot reach the eDRAM** [C: probe 2, only the ME's kernel segments 0x80000000 / 0xA0000000 reach it; our main CPU runs in user mode].
