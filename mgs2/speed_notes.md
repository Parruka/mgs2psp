# MGS2 PSP port: where a deck step's time goes, and the speedups (2026-10-18, updated 2026-10-19)

Measured on x86 (the probe, same generated C as the PSP build) unless a line says PSP. Game-derived data stays in the container; this file has numbers only. (Two EE RAM dumps that a relative MGS2_EE_DUMP prefix wrote to the shared folder on 2026-10-20 were deleted on 2026-10-23 with Ffm's OK, audit L11; boot.c now refuses a relative or /mnt/ prefix.) PSP numbers come from Ffm's runs of the timing harness (psp_harness.md); none yet.

## 1. Deck frame profile (callgrind, vblanks 24000-24099, Tanker deck idle)

valgrind ignores the MXCSR round-to-zero setting, so this run follows the round-to-nearest path; its hashes match `boot/hashes_w00a_x86.txt` (RN reference) at every 100 vblanks from 23000. Build: `/home/claude/mgs2cut/bootprof` (boot.c `MGS2_CALLGRIND`, `MGS2_PROF_VB=a:b`; the hook's own hash/dump work is left out).

- 150 M x86 instructions per vblank.
- **The draw pipeline is 80%.** `0x11da90` (DG_ActLast candidate, `decomp_names_sles.md`) -> `0x11ee98` -> `0x11e5e0` is 80.5% inclusive.
- **The VU0 micro-mode interpreter is 68%** (`vu_upper` 29.7%, `vu_run` 24.2%, `vu_commit` 6.8%, `vu_lower` 6.4%), almost all of it called from inside the draw pipeline: 0x11f968 (about 700 calls per vblank), 0x13bd00 (about 450 per vblank), 0x12dc50, 0x11fde8, stage 0x3bebf0. About 1,700 micro calls and 114 k micro steps per vblank, about 890 x86 instructions per step (the interpreter models the pipeline per step). Outside the draw pipeline: the collision's VIF0 MSCAL, about 1%.
- **The virtual-clock poll was 16%.** Every loop back-edge (about 60 k per vblank) scanned the 64 alarm slots (`k_events_due`, about 400 x86 instructions per poll; about 330 MIPS instructions on the PSP build). Fixed, see section 3.
- GS packet walk (VIF1/GIF DMA model): about 2% after the bulk walk.

## 2. A deck step without the draw pipeline

Experiment (`/home/claude/mgs2cut/bootstub`, dispatch.h `GEN_STUB_HOOK`, `MGS2_STUB=11da90:24000`): from vb 24000 the call to 0x11da90 returns at once. The game keeps running on the deck (no new stage, no stop). Host time per vblank, two runs side by side on a loaded machine (absolute values inflated, the ratio holds):

| vblanks | full game | draw pipeline skipped |
|---|---|---|
| 24001-24100 | 12.9 ms | 2.3 ms |
| 24101-24500 | 10.7-12.8 ms | 0.6-3.1 ms |
| 24501-25200 | 10.3-16.7 ms | 0.8-7.0 ms |

So the logic, the IOP/sound model and the rest are roughly 10-25% of a full deck step on x86. The GE renderer replaces the draw pipeline (TT method), so this part is what the PSP must run twice per 25 fps frame. The PSP harness v2 times the draw pipeline separately on hardware (section 4).

## 3. Exact speedups done (game state unchanged, x86 hashes identical to vb 25200)

| Speedup | Where | x86 effect |
|---|---|---|
| GS-side walk skips VU/IMAGE data in bulk | runtime/ee_io.h `dma_run` + block walkers (`OPT_GS_BLOCK`) | GS walk 2% of the deck step |
| Poll scans alarms only once an event is due | runtime/kernel.h `k_due` (`OPT_POLL_DUE`) | whole boot-to-deck run 110 s -> 87 s |
| Thread pick scans only created threads | runtime/kernel.h `k_pick` / `k_th_hi` | k_pick was 7.7% of a quiet PSP step (PspProf) |
| One VU0 interpreter copy for all units | runtime/vu0.h `vu_run_shared` | smaller code; every micro call goes through one place (AOT, checks) |
| Inline loop poll (2026-10-19) | tools/poll_fast.py on the generated headers, gen_pre.h `IRQ_POLLF`, kernel.h `k_poll_at` / `k_poll_arm` | a back-edge is `k_time += 64` and one compare; registers are stored and the poll runs only when an interrupt, event or thread switch is due. rt_poll was 2.7% of a busy PSP step plus a register flush per iteration |
| Native qword copy (2026-10-19) | recomp/idioms.py `QCOPY` (the routine's exact words, in 108 stage images), tools/idiom_apply.py, boot.c `rt_idiom_qcopy` | same loads and stores in the same order, same registers and virtual time; falls back to the translation when an address is not plain RAM or a poll would fire. Boot-to-deck: 9.8 M calls native, 1 left to the translation. Was 6.3% of a busy PSP step |

Both can be switched off at run time (`g_opt`, runtime/host_time.h); switching them every 100 vblanks for the whole run (`MGS2_OPT_CYCLE=500:100`) still gives identical hashes, which is what lets harness v2 time them against each other in one PSP run.

## 5. PSP cost profile (PspProf, 2026-10-19, harness v2 before the 2026-10-19 speedups)

The container's PPSSPP with the TT PspProf patch (psp_harness.md "Emulator profile"): instructions + 125 cycles per simulated I- or D-cache miss, at 333 MHz. Draw pipeline and GS walk excluded (the GE renderer replaces them), so this is the logic step.
- Busy deck steps (vb 24001-24100): 14.7 M instructions, 78 k I-misses, 44 k D-misses: about 90 ms. Game code (stage) 33 ms, game code (ELF) 23 ms, VU0 / VIF0 model 18 ms, other runtime 7 ms, kernel / poll 7 ms.
- Quiet deck steps (vb 24151-24350): 1.0 M instructions, 12.9 k I-misses, 9.2 k D-misses: about 11 ms; cache misses dominate.
- 25 fps needs two 50 Hz logic steps per 40 ms frame. Quiet steps fit; busy steps were 4-5x over before the speedups of section 3.
- Ideal code layout: 8% fewer I-misses (about 2.4 ms of a busy step). Small next to the items below.
- These numbers predate the VF00 fix (section 6): the busy range ran the slerp micro program 33268338 about 250 times per step; with VF00 fixed that range runs different programs (section 6). Re-profile on the v3 build.

## 6. VF00 (2026-10-19): a fidelity fix that also cuts VU0 work

The VU's VF00 is hardwired to (0, 0, 0, 1.0). boot.c never called `vu_reset`, so the micro programs and the macro ops not specialized by vuemit.py (which already used the constants) read VF00.w as 0: every `div q, vf00w, ...` reciprocal and every w = 1 was 0. Fixed in boot.c (`vu_reset` at start; `MGS2_NO_VF00` keeps the old state for comparisons).
- Same stage sequence (n_title 400, r_tnk0 3100, d00t 3500, d01t 20100, w00a 23200), deterministic (three runs, same hashes), every RAM hash differs from vb 100.
- VU0 work to vb 25200: 8.2 M micro calls and 487 M steps, against 9.7 M and 644 M before (24% fewer steps).
- Deck: player position and actor list identical to the old run up to vb 23800; from about vb 23900 the two runs differ (the scripted pad gives no input after vb 23156). Which matches the console cannot be checked here; VF00 = (0, 0, 0, 1) is the hardware's.
- New references: `boot/hashes_x86_rz_vf0.txt` (VF00 on). The old `hashes_x86_rz.txt` is still what `MGS2_NO_VF00=1` must give.
- The reduced build needs the coverage of both runs (90 functions more): v3 headers are pruned with the union of both coverages.

## 7. FCGET (2026-10-19): a second VU0 fidelity fix

FCGET (lower op 0x1c) reads the clip flags & 0xfff (VU manual; PCSX2 _vuFCGET); vu0.h read the status register. Fixed (`MGS2_OLD_FCGET=1` for the old read). Used by the culling programs 148d7d43 / 8baafbc3. Same stage sequence, hashes differ from vb 4300, VU0 work to vb 25200 9.23 M calls / 598 M steps. **Current reference: `boot/hashes_x86_rz_fc.txt`** (VF00 + FCGET). After the fix no boot-path program reads the status flags, so compiled VU0 runs with dead flags (no `VP_EXACT_FLAGS`).

## 10. v5 on the PSP, and exact codegen work (2026-10-19)

- **v5 on Ffm's PSP-3000** (log and steps in `prof/hw_v5/`): all 50 hashes identical to `hashes_x86_rz_fc.txt`; FCR31 reads 01000001 on hardware. Deck steps with all speedups on (301 steps): mean 170.4 ms = logic 74.3 + draw pipeline 79.7 + GS walk 13.6 + IOP/sound 2.8 (median 172, min 144, max 221). PspProf had estimated the logic part at 73.7 ms: the cost model matches hardware here (it was 2x optimistic in TT). The 365 k qcopy calls left to the translation (x86: 17; the PPSSPP run of v5 shows the same count) come from the rotation windows (the native copy declines when a poll is due): runs with `MGS2_OPT=ffffffff` (no rotation) leave 17, as on x86.
- **VU_MCL_RZ** (vu0.h, `-DVU_MCL_RZ`): under the PSP's fixed FPU mode (round toward zero + flush to zero, never changed: guest cfc1 / ctc1 are no-ops) the macro-op result clamp is the identity, so it is dropped. Build D: PPSSPP hashes 50/50, PspProf busy logic step 73.7 -> 67.9 ms. The hardware FCR31 above confirms the mode.
- **-Os for the generated units** (build E): game code 7 ms faster, but the out-of-line helpers cost more; 78.3 ms. Not used.
- **Stack accesses** (`tools/sp_fast.py`, gen_pre.h RD*S / WR*S): a $sp + k access skips the I/O test and masks $sp once. x86 with `-DGEN_SP_CHECK`: hashes identical to vb 25200 and no access breaks the invariant. w00a: 5,864 loads and 5,380 stores rewritten.
- **Per-register widths** (`RC_PERREG=1` in regcache.py; `RC_NCHK=1` + `-DGEN_NCHK` checks every narrow load on x86): only the registers whose upper half can matter stay int64_t in a 64-bit function. The first version diverged at vb 31 (64-bit values passed through moves lost their upper half); spreading 64-bit-ness both ways fixed that, but the deck still diverged from vb 23257 (a compare on a zero-extended 0xffffffff), so compare operands now stay 64-bit too. That keeps 61% of the registers of the hot 64-bit functions wide (cost-weighted), so the gain is small.
- **Profile-guided build** (psp/Makefile `PGO=gen` / `PGO=use`, main_psp.c `pgo A B`): the instrumented build does not fit in memory at once (56.5 MB), so two emulator runs: A = main ELF + runtime instrumented, B = overlay w00a instrumented; both with `MGS2_OPT=ffffffff` (no rotation) and counts from vb 24000 to 25150.
  Use build: psp/Makefile `PGO=use` with the gcda files of both runs in the build dir (named like the objects); flags `-fprofile-use -fprofile-partial-training -Wno-missing-profile` and no unroll / peel / tracer / ipa-cp-clone / unswitch / split-loops / predictive-commoning (they grow code; I-misses dominate). Any change to a profiled source changes its CFG checksums: re-profile. **Build U** (base headers + VU_MCL_RZ + PGO): PPSSPP hashes 50/50; PspProf busy logic 67.9 -> **58.1 ms**, full deck step (draw pipeline and GS walk included, `prof A B all`) 174 -> **141.9 ms**. Delivered as **MGS2T_v6** (2026-10-19). Summaries `prof/V6U_busy_summary.txt`, `prof/V6U_all_summary.txt`.
- **Hot / cold splitting** (`-freorder-blocks-and-partition`): the link fails (MIPS branches across the split use R_MIPS_PC16, +-128 KB) and only about 12 KB would move. Dropped.
- **Per-register widths:** exact with the compare rule (x86 252/252) but only 0.5% smaller code. Not used.
- **sp_fast + VFPU qcopy + PGO (build SPU, re-profiled):** PPSSPP hashes 50/50. qcopy through lv.q / sv.q (boot.c, one qword at a time in order, g_mem 64-byte aligned, main thread has THREAD_ATTR_VFPU): 804 k -> 247 k instructions, 5.6 -> 4.2 ms. Instructions per full step 21.5 M -> 20.6 M, but I-misses 122 k -> 133 k: the hot draw loop's code (vup_8baafbc3_0, vuc_dispatch, P11fde8, P11f968, P13bf78) landed on conflicting cache sets. Busy 57.1 ms (U 58.1), full step **144.6 ms** (U 141.9). Not delivered: code placement moves the result by several ms either way; the I-cache is 16 KB, 2-way, 64-byte lines (128 sets), and the draw loop's hot functions are 7-33 KB each.
- **VU0 clamp hoisting** (`tools/vu_hoist.py`, gen_pre.h IRQ_POLLV / VH_CHK, boot.c g_vu_ext): in a simple loop, the input clamps of VF registers the body never writes, and the ACC clamps, move to the preheader. The runtime's slow paths that can change VF / ACC behind generated code (rt_store, rt_poll_slow) bump g_vu_ext; a loop that stores checks it at the top and after a store that is followed by a hoisted read, and redoes the clamps if it moved. First version (no stores, 1 loop: P12dbc0, 16 clamps per iteration): x86 252/252. With stores: elf 9 loops / 136 clamps per iteration, d00t 6 / 70, w00a 5 / 67.

## 11. Code layout against the I-cache (2026-10-19)

- **Conflict share.** PspProf with `PSPPROF_FA=1` also runs a fully associative LRU I-cache of the same size. Full deck step: build U 121.9 k I-misses (2-way) vs 98.5 k (fully associative), build SPU 133.1 k vs 94.9 k: 19-29% of the I-misses come from where the code sits, not from how much runs.
- **Trace.** `PSPPROF_ITRACE=<file>` (PspProf.h, local change): the counted fetches as runs of sequential pcs (uint32 pc, uint32 length). Build SPU, `prof 24001 24011 all` (10 full steps): 14.9 M runs, 119 MB. Hot code: 645 main-ELF functions (1.70 MB) and 322 overlay functions (1.46 MB).
- **Simulator** `tools/layout_sim.c` (functions from `tools/layout_funcs.py`): replays the trace on the PspProf cache with functions moved as units. On the current placement it gives exactly PspProf's count (1,261,242 I-misses for the 10 steps). A layout = per region (main ELF .text, overlay code) the fetched functions in an order from the region's start, 4-byte aligned (gcc's function sections), then the rest. Search: simulated annealing (swap / move one function) on the misses of the first 2 steps, from the better of the current order and first-fetch order.
- **Result (model, build SPU):** ~~-39%~~ wrong: layout_sim's `-base0/-base1` parse was unsequenced (`sb[argv[i][5]-'0'] = strtoul(argv[++i])`), so `-base1` overwrote region 0's base and the search placed the main ELF's code 0x367ff8 too high. Fixed 2026-10-19; real relinked addresses now give exactly the simulator's count (`layout_sim -in <order> -new <relinked funcs>`).
- **v7 (build VHU = SPU + vu_hoist, re-PGO; LAYOUT=1):** 10-step trace 1,066,000 I-misses as linked; first layout (wrong base) 845,119 real; re-optimized with the right bases (25,000 moves on steps 6-8, seed 12) **801,040, -24.9%** (a second search on steps 3-5 gave 817,868). Order saved as prof/layout_order_v7.txt. PspProf: full deck step 130.8 -> **120.8 ms** (I-miss 107.7 k -> 80.8 k per step), busy logic 55.7 -> 52.0 ms; hashes 50/50 in PPSSPP (prof/hashes_v7_ppsspp.txt). Model full step v6 141.9 -> v7 120.8 (-15%); the model read 7% high on v6 hardware.
- **Applying it** (psp/Makefile `LAYOUT=1`, `tools/layout_order.py`): -ffunction-sections for the game code and the runtime; `layout_elf.ld` goes to ld `--section-ordering-file` (the listed sections go first in .text); `layout_<stage>.ld` is inserted after the overlay header in ovl.ld. main_psp.c aligns the overlay arena to 8 KB so the overlay's sets do not depend on the main ELF's size. Only placement changes: relinking needs no recompile, and the trace stays valid for any order of the same objects (`layout_sim -new` checks a relinked build's real addresses).
- **Where the data misses are** (PspProf `PSPPROF_DHIST=1`, local change: D-misses per 1 KB of data address; build SPU, busy logic, 38.6 k per step): guest RAM 66% (of which the guest scratchpad, RAM 0-16 KB under GUEST_SPR0, 12.6%: it cannot move, the address mask maps it into g_mem), the main thread's stack area (0x0bd00000) 5%, then host-side VU0 / context arrays: VUPROG 3.5%, VF 3.1%, R 3.0%, g_spu 1.7%, VUMEM 1.6%, k_th 1.2%, g_env 0.9%. Those small hot arrays miss only through conflicts; the PSP's own 16 KB scratchpad (0x00010000, no cache) could hold them: about 6-12% of the data misses, 1-2 ms per logic step (not done yet).

**Idea (not done; exactness first).** At 25 fps with 50 Hz logic, every other step is never displayed. ## 16. VIF0 and scratchpad DMA fast paths (2026-10-19, exact)

**Why the ropes cost 8.3 ms.** Each rope runs 9 sub-steps per logic step; each sub-step runs a VU0 macro-mode loop (stage 0x3b89e0, 12 k PSP instructions per call) and a collision query (0x14d860) that sends one VIF0 DMA: an MPG upload of the query's micro program, a few UNPACKs and two MSCALs. ## 18. Where the busy logic step's cost comes from, by code (2026-10-19, v8 PspProf per-PC counts, tools in this section are scratch)

Busy deck logic step (V8a_busy, buildvf, 100 steps): 6.25 M instructions (18.8 ms), 50.6 k I-miss (19 ms), 35.8 k D-miss (13.4 ms).
- **Code size is about 8 PSP instructions per PS2 instruction, wide or narrow.** gen_s_w00a.o: 86.6 k guest instructions -> 2.76 MB of functions (7.98 per guest instruction; 64-bit functions 8.1, 32-bit 7.6); gen.o: 71.0 k -> 2.36 MB (8.3; 64-bit 8.2, 32-bit 8.5). So **narrowing more functions to 32 bits is not a lever** (the hot 64-bit idioms, e.g. line_sph's LCG `multu; mflo; mfhi; dsll32 ...; daddiu 1; dsll32; dsra32`, are already folded by GCC to `maddu; mflo; addiu`). By regression over functions, each loop poll site costs 106-178 instructions of code (its flush and the call's spills, mostly cold), a guest store 2-10, a load 2-6.
- **Half the I-misses come from lines that miss 10 or more times per step** (1,098 lines, 24.6 k misses; another 2,163 lines miss 3-10 times, 12.3 k): code reused inside one step whose path is larger than the 16 KB I-cache, so layout cannot fix it. Top: the rope sub-step path, run 18 times per step (vup_43da1f40_0 2.1 k, P2ec188 1.7 k, P14d860 1.5 k, P3beee8 1.1 k, gen_call 1.0 k, io_flush 1.0 k, P3b89e0 0.9 k, P3bf860 0.9 k, the libvu0 rotations P166090 / P166108 / P1661b0 / P166258 2.7 k together, P14d1c8 / P14d510 / P14d000 1.4 k), and vup_33268338_0 1.0 k. Those small functions are 26-37 guest instructions but about 2 KB of code each: a VU0 macro op becomes about 25 PSP instructions (per component: VN / VACC loads and stores, the input normalization).
- **D-misses**: rt_idiom_qcopy 8.3 k per step (23%), memcpy 3.1 k (9%, DMA copies), P3b89e0 1.6 k, io_flush 1.1 k, P319078 1.1 k, P16cff8 1.0 k. By address (SPU full-run histogram): guest RAM 53%, guest scratchpad (RAM 0-16 KB) 13%, the guest register file and VU0 state (R, RH, F, VF, VN, k_time, VUMEM) about 12%.
- **VU0 share**: compiled micro programs 0.36 M instructions and 4.3 k I-miss per step; game functions whose lines are at least 20% VU0 macro ops 1.71 M and 9.6 k. Together about 11 ms by the cost model: the part a VFPU backend could shrink, if the hardware probe shows VFPU arithmetic equal to the FPU's round-toward-zero.
- **Guest memory checks**: 135 k checked accesses per step (`srl 28` + branch + `ext` + base add, about 4 extra instructions each, 8.6% of instructions). Accesses that reuse a base register already checked in the same block: 37% static, about 33 k per step dynamic: one range check per base would save about 0.1 M instructions (0.3-0.4 ms). Exact by construction (one check of base and the block's offset range, else the per-access path).
- **Loop polls**: about 20 k per step, each about 11 instructions (64-bit k_time add and compare, 3 loads, 2 stores). A 32-bit countdown (k_left -= 64; <= 0 -> slow path, which re-derives k_time and re-arms) would be 4: about 0.15 M instructions (0.4-0.5 ms). Exact.
- **LO / HI** are globals: every multiply stores both halves of both (4 stores; about 23 k multiplies / divides per step). As cached locals: about 0.2 ms.
- **Compiler scheduling flags** (w00a unit, weighted by the busy step): `-fno-schedule-insns` +0.11% instructions / +0.28% I-miss, `-fsched-pressure` +0.55% / -0.08%; stack accesses unchanged. Not a lever.
- **The shared LCG seed 0x1fc954 is stage-local**: only w00a overlay code touches it (38 functions); no main-ELF function does.

**What this means for the 25 fps target.** 25 fps with 50 Hz logic needs 2 logic steps per 40 ms, so logic of about 15-17 ms per step; it is 50.2 ms now (buildv9). The exact levers measured so far are each 0.2-1 ms (layout, memory checks, polls, LO / HI); the larger ones are the VFPU for VU0 work (up to about 5-6 ms, only if the probe allows it) and skipping render-only actors on undisplayed steps (about 4 ms average, §15). That is an estimate, not a measurement: it leaves logic around 35-40 ms on this scene, so the deck would not reach full speed with exact changes alone. The heaviest work is the effects (rain, splashes, sea, rain lines, ropes: about 25 ms of the step, §15), whose only links to the rest of the game are the stage-local seed and the shared work area.

## 39. v23: the VIF1 chain walk in one loop, native sort keys, a DMA register table (2026-10-21)
- **What the walk costs (v22 model, deck vb 24001-24100):** the walk of the VIF1 chain is there only for the GS FINISH / SIGNAL writes that raise the interrupts the game waits on (gif_qw -> gs_reg_write -> k_intc_raise). Per step it walks 11.4 k DMA tags, every one with TTE (two VIF words in the tag): about 7.6 k `ref` and 3.7 k `cnt`. v22 spread it over vif1_word 1.05 M instructions, dma_vif1_block 0.50 M, dma_feed 0.50 M, dma_run 0.30 M and io_flush 0.49 M: 2.84 M instructions, 2.2 k I-misses and 5.5 k D-misses, 13.5 ms of the model's 79.2. The cost is per tag and per VIF command; about 28% of the tags miss the D-cache.
- **First form (build gf, not kept):** a chain fast path that still called vif1_word for the two TTE words of each tag: model +1.76 ms (few instructions saved, and the code order went stale).
- **v23 form (`runtime/ee_io.h` vif1_chain_fast, OPT_GS_FAST 128 with OPT_GS_BLOCK):** one loop over the tags with the VIF1 state in locals (`VifLoc`: words left of the current command, the command, CL / WL). TTE words and data in RAM or the scratchpad are walked inline (`vif1_fast_words`); data that is not DIRECT is skipped in bulk (DIRECT IMAGE data too, as dma_vif1_block does); DIRECT data still goes through gif_qw. A transfer across the 32 MB mask or the scratchpad's end goes through `vif1_run_any`. The VIF1 state is written back at the end, so the next transfer continues where the old walk would. **x86:** hashes = the v21 references on both routes, and the "GS:" statistics line (GIF tags per path, FINISH, SIGNAL, VIF1 command counts) equals the old walk's (MGS2_OPT=ffffff7f) on the deck.
- **Native sort key (`boot/native_elf.c` / `.h`, `tools/native_elf_apply.py`, OPT_NAT_KEY 256):** P12dbc0's loop at 0x12dc00 (the mean clip w of an effect mesh's vertices, re/pipeline_hot.md §1.2) runs natively when the vertices are plain RAM and no poll inside it would reach k_poll_at. Otherwise the translation runs the loop from the same state. The tool hooks gen_elf.h at exact lines (it stops if the generator's output changes), so every other generated function keeps its place and its PGO profile. **x86:** hashes = v21 references on both routes; a check build (`-DNAT_DBC0_CHECK`) ran all 4,471,929 deck loops both ways and compared ACC, VF1, the time, r12, r13 and the fallback count after each: 0 different. No loop needed the translation on either route (deck 4.47 M, crew deck 3.87 M loops).
- **io_flush DMA register lookup:** a write to a DMA channel register found its channel by scanning the 10 channel bases; a 22-entry table indexed by (address - 0x8000) >> 10 gives it directly (`io_dma_at`, checked equal to the scan for every address). ## 40. The FPU rule for denormal operands: the PSP's against the PS2's (audit M1, 2026-10-23, x86)
- **Question (audit M1):** since v16 the reference follows the PSP's FPU (x +- 0 returns a denormal x unchanged; denormal operands are used exactly), where the PS2 treats denormal operands as zero. Does that change anything the game does?
- **Method** (`tools/dev/m1den/`, results `prof/m1_denormal_2026-10-23.txt`): the v21 x86 reference with every lwc1 / mtc1 site of the generated code recorded (build A, PSP rule; its hashes equal the v21 references on both routes: ee / iop / vfb 0 of 252, dense 0 of 559, vuh 0 of 311). Build B: the same binary with `MGS2_M1_PS2=1` (MXCSR DAZ + FTZ + RZ; FADD / FSUB without the zero rule). Both routes to vb 25200, plus the VIF1 + GIF DMA data hashed every vblank (`MGS2_PKT_HASH`).
- **Counts (deck / w01a):** 640.3 M / 583.5 M lwc1 and 306.6 M / 265.6 M mtc1; denormal bit patterns in 16.7 M / 16.3 M lwc1 and 38.1 M / 34.4 M mtc1. 99.9% are integers: 1,274 / 1,014 sites are next used by cvt.s.w on the same register (no branch or label in between), which neither rule touches.
- **Denormal float operands: 5 sites, 63,268 / 46,983 uses**, all stack words at 0x1b47c0-0x1b47d8: P11cf88 0x11cfa8 / 0x11cfa0 and P11ce30 0x11ce70 (vb 15765-25199, next use c.lt.s), d00t P28dd68 0x28e338 / 0x28e38c (vb 4258-4326, 113 uses, mul.s). The zero rule acts only in P11cf88, a 4-lane arctangent (VU0 polynomial at 0x11d02c): 35,019 / 24,072 lane evaluations. Its lane z inputs are stale stack words; [I] its caller (probably w00a 0x3c0728, from the stack layout) fills lanes x and y and reads only out[0] and out[1].
- **Result: B equals A in everything the game keeps or sends.** ee 0 of 252, iop 0 of 252, dense ee 0 of 559, vuh 0 of 311 on both routes; the VIF1 + GIF data of all 25,199 vblanks equal. Only vfb differs (the count of VFPU group runs that fell back to the exact C forms, boot.c:79): B has 20,699 more fallbacks by vb 19,700 (deck 461,571 A, 482,270 B), because lane z = +Fmax (DAZ: 0 +- d = +0, then 0 / 0 = +Fmax) overflows the polynomial where A has -d / d = -1. VF registers differ in lane z only and are equal again by the next vblank.
- **Limits:** these two routes only; the hashes see state at vblanks and the GIF data, not VU1 memory or the GS's own output; B models only the denormal rule (no R5900 handling of exponent-255 words, SSE zero signs; the R5900's sign of 0 / 0 is unverified).
- **What the PS2 rule would cost on the PSP:** a check on each float loaded by lwc1 / mtc1 and used as a float: 946.9 M loads over the deck route's 12,600 steps, about 75,000 per step on average (the integer sites need the recompiler to see the cvt.s.w). Not measured.
- **Recommendation (asked of Ffm 2026-10-23):** keep the PSP rule (no cost, identical on both routes, and 20,699 fewer slow fallbacks), and run build B on every new route as a check: a difference names the site to look at.
- **Decision (Ffm, 2026-10-23 12:49, decision card "Keep PSP rule"):** the port keeps the PSP's rule. Standing check: every new route or area also runs on x86 as build B (`MGS2_M1_PS2=1`, `tools/dev/m1den/README.md` "Use for a new route"); its ee / iop / vuh hashes and per-vblank VIF1 + GIF data must equal build A's, and a difference names the site to fix.
