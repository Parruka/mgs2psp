# Is MGS2's logic tied to the frame rate? (SLES-50383, PAL)

2026-11-07, thread "Prove whether game logic is tied to the frame rate", Ffm 21:03-21:04. Follows halfrate_study.md.
[C] = read in the code or measured. UNKNOWN = not proven yet, with how we find out. No guesses.

**Premise corrected:** this disc is PAL (SYSTEM.CNF: VMODE = PAL). The game steps at 50 Hz, not 60. One step per vblank when the step fits in 20 ms; the in-engine cutscenes run 25 steps a second through the wait word 0x18db74 [C].

## 1. Answer by subsystem

**Global [C]: the game has no delta time.** One step = one GV_ExecActorSystem call (0x13f140), which calls each actor's act function with the actor as its only argument. Act1 (0x11d9d0) computes the vblanks since the last step and stores them at 0x18db6c. The only reader of that word in the ELF is 0x1058e0 (GM_ExecProc: `play_time += elapsed`), and none of the 25 stage images checked earlier read it (speed_notes §16). Hardware time sources read by the ELF:

| Source | Readers [C] | Use |

**Correction 2026-11-07 22:40 (from the twin, MGS2 port thread):** the link-variable block at the pointer in 0x18f6d4 is moved at stage loads by an anti-cheat shift (HD source libgcl/anti_par.c: 0-1020 bytes from an hsync-timer seed, whose low bit also picks the order of the link and script variables). Its site is in stage code, not the ELF (found 23:12, see the table below). **What this means [C]:** gameplay moves, cameras, AI counters and animation are tied to the step. Four things follow the vblank count instead: play time, the in-game clock, the w01a random-generator stepping, and cutscene pacing. The link block's place follows the timer. In the port, 0x18db64 is the twin's virtual count (hashes are equal on x86, the emulators and the PSP), so all of them behave like a PS2 that never drops a frame, whatever the PSP's real speed. **Rule for 25 fps:** the virtual vblank count must keep advancing exactly as now (one per 50 Hz step outside the cutscene wait word); tying it to the PSP's real time would change the random sequence on the deck. Whether the twin's count ever advances by 2 in a normal step is UNKNOWN; the twin's per-step log of 0x18db6c on route i will show it. **Shared random seed (twin census 23:48, prof/hr2_route_i/seed_users_route_i.txt) [C]:** each stage has one random seed (w01a 0x1fbd74, w00a 0x1fc954). The guards (attacker, watcher, eneequip, usp, command, KR_RandS / KR_RandU; S_w01a_P2b4238 = SIG_BasicShoot, which calls ENE_ShootBullet 0x251ed8) and the effect actors all step that one word. On the deck almost every step comes from effects: item_box 987,648, body_sph 731,692, d_splash_floor 306,229, chim_smo 293,776, charaspread 120,504, d_splash_camera 107,350, d_splash_fall 96,147, ripple 31,542; the guards' helpers 60. **So any game-side lightening of an effect actor (running it less often, fewer particles) changes every later random value the guards get: a gameplay change.** Only cuts that leave the state hashes unchanged (draw-side filters, exact skips) keep the guards original. This rules out H2 (cosmetic actors every other step) under the charter, and limits the 21:17 choice "Cut cosmetic effects only" to draw-side cuts unless Ffm decides otherwise. The cuts made so far (rain sprites, streaks, rain exact skips) all kept the hashes, so they are draw-side and keep the guards original [C, hash tests].
- Clock [C]: only hour, minute and second (+104, +108, +112) are read, and only by the clock's own act; year, month, day have no reader on route i. Writers of 0x1cc8b8 by SIF transfer: UNKNOWN (the census sees CPU stores only).
- Twin steps with elapsed != 1 at wait 0: 28 on route i, all at a load or the first step after it [C]. The virtual count advances 1 per step in play.

**Measured [C]** (x86 twin, route i, the MGS2 port thread 2026-11-07 15:56): with 0x18db74 = 2 from vb 30,000, 50 steps per 100 vblanks instead of 100, elapsed = 2, play time at the same rate per second, nothing writes the wait word back. So the game takes a 2-vblank step through its own mechanism and plays at half speed.

## 2. How to show 25-30 fps with the logic unchanged

| Option | Logic identical? | Speed / pacing | Verdict |
|---|---|---|---|
| **A. Fixed 50 Hz steps, show every 2nd (the port today)** | yes, bit for bit (state hashes equal x86 / emulators / PSP, every build since v13) | 25 fps at full speed when 2 steps + a picture fit in 40 ms; slower than that, the game slows down with it | **recommended**; the only option that keeps the original logic |
| A'. As A, plus a time-driven skip of pictures (show 1 of 3 steps when late) | yes | keeps game speed at the cost of fps (16.7) | possible; display-only, goes in DEVIATIONS.md if used, needs your OK |
| B. Half-rate step with scaled constants | **no**: every speed, timer, AI counter and script wait changed; collisions over doubled moves differ | 25 steps a second | rejected under "original game logic" (halfrate_study.md) |
| C. 30 fps from 50 Hz steps | yes | shows 3 of 5 steps: 2-1-2 step gaps, uneven motion | not recommended; 25 is the natural PAL rate |
| D. 60 steps a second (NTSC rate) | the steps are identical, but the game runs 20% faster than the PAL disc | | UNKNOWN whether the PAL build scaled its constants for 50 Hz; would be found by comparing with an NTSC executable. Not the original PAL behaviour either way |

**What A needs on real hardware:** every pair of steps plus its picture within 40 ms. With the ME drawing in parallel, the main CPU must run 2 steps of game code in 40 ms, about 20 ms a step. Measured today on your PSP (gl16 run 1, rainy aft deck): 71.3 ms a step of game code (logic 41.8 + draw pipeline 29.5) and 70.7 of picture [C]. After all planned exact work the estimate is 28-40 ms a step of game code there [I, roadmap], so 25 fps on the rainy deck with identical logic is not reachable on today's plan: 11.5-16 fps there [I]. Inside the ship the estimate is 19-25 fps [I]. Only PSP runs settle these.

**Your choice (card, 2026-11-07 21:17): "Cut cosmetic effects only".** Where the original logic can't reach 25 fps, weather and effect actors may be lightened, each logged in DEVIATIONS.md with pictures and agreed with you first; gameplay logic stays original and option B is out.

**Narrowed by your choice (card, 2026-11-08 00:09): "Drawing-side cuts only".** Because the guards and the effects share one random seed, heavy-scene cuts must leave the state hashes unchanged (draw-side filters, exact skips). No game-side thinning of effect actors; H2 is out. So on the rainy deck, logic savings can only come from exact work: 25 fps there is not reachable on the current plan [I, deck_costs.md: logic about 30 ms a step after exact work against 20].
